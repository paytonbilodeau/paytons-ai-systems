# Approval Rules

Enter these as natural-language rules in the platform's approval or review feature. Add the require rules first; require rules take precedence over allow rules.

## Require approval

1. Require approval before sending any email, message, invitation, reply, direct message, form, or notification to another person.
2. Require approval before publishing, scheduling, editing, deleting, or replying to any public social post.
3. Require approval before any purchase, payment, refund, transfer, subscription, booking, bid, price commitment, or financial action.
4. Require approval before deleting, overwriting, moving, renaming, or changing permissions on any file outside the approved staging folders.
5. Require approval before changing a production website, database, CRM, customer record, automation, schedule, deployment, DNS record, account setting, or access control.
6. Require approval before accepting legal terms, signing up for a service, creating an account, or committing me to an agreement.
7. Require approval before installing software, plugins, packages, browser extensions, remote-control tools, model proxies, or code from the internet.
8. Require approval before creating, displaying, rotating, exporting, or storing an API key, token, credential, cookie, authentication file, passkey, or secret.
9. Require approval before running privileged commands, changing ownership or permissions, starting or stopping a service, or changing files outside the approved work scope.
10. Require approval before modifying my canonical memory, instruction, skill, automation, or script files during the pilot.

## Always allow, only after the rules above exist

1. Always allow read-only searches and file inspection inside the approved workspace, except secret-bearing files and paths named in my boundary list.
2. Always allow standard read-only file and version-control commands used within the approved workspace.
3. Always allow writes inside the named staging folders: [list the exact folders].
4. Always allow documented dry-runs and read-only health checks that change no external state.
5. Always allow research, drafting, local analysis, inventories, and handoff files within the approved scope.
6. Always allow read-only connector calls after the connected identity and scope have been verified.

## Standing instruction for the front door

Proceed without asking for every safe, reversible step that is already within the requested task and the rules above. Ask only at the exact point a credential, irreversible action, external write, new cost, new access scope, or material change requires me.

Do not use a blanket rule such as "allow everything in the browser" or "always allow all commands."
